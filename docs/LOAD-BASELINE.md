# Нагрузочный baseline (локальный замер)

Замер снят на машине разработчика, **не на проде**. Числа нужны, чтобы понимать
порядок величин и видеть, что упирается первым, а не чтобы обещать ёмкость.

## Окружение

| Параметр | Значение |
|---|---|
| CPU | AMD Ryzen 7 5700U, 8 ядер / 16 потоков |
| RAM | 7.3 GB |
| ОС | Windows 10 Pro |
| Сервер | `uvicorn src.api_pkg:app`, **1 воркер**, порт 8099 |
| БД | PostgreSQL 17, локально, та же машина |
| Инструмент | `tests/load/http_loadtest.py` (httpx + stdlib) |

Один воркер выбран намеренно: так видно потолок одного процесса, а не сумму.
На проде за reverse-proxy обычно несколько воркеров, и цифры умножаются не
линейно (общая БД, общий пул соединений).

## Как воспроизвести

```powershell
# 1. Поднять приложение
.\.venv\Scripts\python.exe -m uvicorn src.api_pkg:app --host 127.0.0.1 --port 8099

# 2. Замер с включёнными лимитами (как видит реальный пользователь)
.\.venv\Scripts\python.exe tests\load\http_loadtest.py `
    --base-url http://127.0.0.1:8099 --duration 20 --concurrency 10

# 3. Замер без лимитов (чистая мощность сервера)
#    перезапустить приложение с RATELIMIT_ENABLED=false, затем повторить п.2
```

Скрипт делает один `POST /api/auth/login` (берёт учётные данные из переменных окружения `LOADTEST_EMAIL` / `LOADTEST_PASSWORD`; если они не заданы — опционально использует локальный `users.json`, который gitignored и не поставляется с репозиторием), Повторный запуск добавляет одну
строку сессии — данные не портит.

## Результаты

### С включёнными rate-limit (реальный пользовательский путь)

| Эндпоинт | Conc | RPS | p50, мс | p95, мс | p99, мс | Ошибки | 429 |
|---|---:|---:|---:|---:|---:|---:|---:|
| `GET /health` | 10 | 178.1 | 45.2 | 77.3 | 86.8 | 0.0% | 0 |
| `GET /api/vacancies?limit=20` | 10 | 98.0 | 133.9 | 713.8 | 734.0 | 97.0% | 1914 |
| `GET /api/taxonomy/categories` | 10 | 133.7 | 57.1 | 68.9 | 69.8 | 97.8% | 2620 |

97% ошибок здесь — это **не сбой**, а `429 Too Many Requests`: slowapi режет по
60 запросов в минуту на IP. Один клиент с 10 потоками выбирает лимит за секунды.
Так и должно быть; цифра показывает, что ограничитель работает.

### Без rate-limit (`RATELIMIT_ENABLED=false`) — мощность сервера

| Эндпоинт | Conc | RPS | p50, мс | p95, мс | p99, мс | Ошибки | 429 |
|---|---:|---:|---:|---:|---:|---:|---:|
| `GET /health` | 10 | 121.5 | 49.3 | 85.0 | 100.9 | 0.0% | 0 |
| `GET /api/vacancies?limit=20` | 10 | 75.4 | 90.9 | 152.1 | 720.0 | 0.0% | 0 |
| `GET /api/taxonomy/categories` | 10 | 86.2 | 85.2 | 123.1 | 161.4 | 0.0% | 0 |

Ошибок нет ни одной — при снятом лимите сервер держит нагрузку.

## Что упирается первым

1. **Один процесс uvicorn.** `/health` (без БД, без данных) даёт всего ~120-180
   RPS при 16 потоках CPU: узкое место — не CPU, а event loop одного процесса и
   накладные расходы asyncio-планировщика на мелких запросах.
2. **`/api/vacancies` — самый тяжёлый.** p99 = 720 мс при p95 = 152 мс: редкие
   запросы попадают на холодный путь (запрос в БД + сериализация 20 вакансий с
   `parsed_skills`/`key_skills`). Хвост в 5 раз хуже медианы — типичный признак
   отсутствия кэша и работы с JSONB на каждый запрос.
3. **`/api/taxonomy/categories` быстрый и стабильный** (p99 161 мс, разброс
   маленький): таксономия живёт в памяти, БД не трогается.

Разброс между прогонами заметный (`/health` 178 → 121 RPS при одинаковых
параметрах): машина делится с другими процессами (БД, редактор, агенты).
Поэтому цифры — ориентир, а не SLA.

## Практический вывод

- Локально один воркер держит ~75-120 RPS на «тяжёлых» эндпоинтах и ~120-180 на
  лёгких, без ошибок.
- Для роста нужен либо второй воркер (проверить, что общий пул БД выдержит:
  `DB_POOL_MAX=10` на процесс), либо кэш на `/api/vacancies` по mtime/параметрам.
- Хвост p99 на вакансиях — первое, что стоит оптимизировать: он в 5 раз хуже
  медианы и портит восприятие отзывчивости сильнее, чем среднее значение.

## SLO-пороги CI (backlog 6.7.4)

Пороги живут в двух местах и должны совпадать:

1. `tests/load/k6_script.js` → `options.thresholds` (первичный гейт: k6 выходит
   с кодом 99 и валит CI-джоб при нарушении);
2. `.github/workflows/load-test.yml` → `env.SLO_*` + шаг `Check thresholds`
   (вторичный fail-closed гейт по `--summary-export` JSON: если метрика пропала
   или формат отчёта изменился, шаг выходит с 1).

| Метрика | Порог (SLO) | Env workflow |
|---|---|---|
| `http_req_duration` p95 | < 800 мс | `SLO_P95_MS=800` |
| `http_req_failed` | < 1% (rate 0.01) | `SLO_ERROR_RATE=0.01` |
| `checks` (доля passed) | > 99% (rate 0.99) | `SLO_CHECKS_RATE=0.99` |

Обоснование чисел:

- **p95 < 800 мс.** CI-сценарий бьёт только по двум самым лёгким бесплатным
  ручкам без БД-тяжести: `GET /api/health` и `GET /` (health-check JSON, см.
  `src/api_pkg/routers/health.py`). Локальный baseline даёт для аналогичных
  лёгких ручек p95 69-161 мс и p99 до ~734 мс на худшем эндпоинте (таблица
  выше). 800 мс = грубый потолок, который в 5-10 раз выше измеренного p95
  лёгких ручек: он не даст ложных падений на медленном раннере GitHub Actions
  и на холодном старте контейнеров, но поймает реальную деградацию в разы
  (утечка пула, блокировка event loop). Как только появятся прогоны на staging
  с реальными числами, порог ужесточаем до 2x от фактического p95.
- **http_req_failed < 1%.** Обе ручки не требуют авторизации и не лимитированы
  slowapi (лимиты навешаны точечно декораторами `@limiter.limit`, для `/` и
  `/api/health` их нет), так что 429/5xx в зелёном прогоне быть не должно вовсе;
  1% - допуск на транзиенты (первый запрос до готовности, сетевой шум раннера).
- **checks > 99%.** Проверка `status === 200` на обеих ручках; 1% допуск
  зеркаляет допуск по ошибкам.

Правило синхронизации: меняешь число в одном месте - меняй в обоих и обнови
таблицу здесь. Формат `--summary-export`: старый пишет `.rate/.value` и ключ
`"p(95)"`, новый (k6 v1.5+, opt-in) - `.values.*`; jq в шаге пробует оба.

## Soak-прогон (backlog 7.5.5)

Скрипт: `tests/load/soak.js`. Ровная нагрузка 5 VU 60 минут (5m warmup +
50m steady + 5m cooldown на 1 VU), те же SLO, что в load-прогоне, плюс
контроль деградации к концу: срез `cooldown` обязан держать p95 < 400 мс
(вдвое жёстче общего бюджета) - k6 не читает RSS сервера, поэтому утечка
памяти/деградация пулов видна как рост задержки на последних минутах.

Запуск (нужен k6: `winget install k6 --source winget` или образ
`grafana/k6`; локально на Windows k6 может отсутствовать - тогда только
синтаксическая проверка `node --check tests/load/soak.js`):

```powershell
# полный почасовой прогон против локального сервера
.\.venv\Scripts\python.exe -m uvicorn src.api_pkg:app --host 127.0.0.1 --port 8099
k6 run tests/load/soak.js            # BASE_URL по умолчанию http://localhost:8000

# дымной вариант ~4 минуты для проверки самого скрипта
$env:SOAK_VUS='2'; $env:SOAK_WARMUP_MIN='1'; $env:SOAK_STEADY_MIN='2'; $env:SOAK_COOLDOWN_MIN='1'
k6 run tests/load/soak.js

# против staging
$env:BASE_URL='https://staging.example.com'; k6 run tests/load/soak.js
```

Итог пишется в `tests/load/reports/soak-summary.json` (handleSummary), артефактом
в CI его можно забрать тем же шагом upload-artifact. k6 выходит 99 при нарушении
любого порога - тот же контракт падения, что у load-прогона.
