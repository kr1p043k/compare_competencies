# RAG: оценка retrieval (golden-set, recall@k, MRR, nDCG@k)

Офлайн-оценка качества поиска без LLM: тот же `RagService`, что у чата, но
`log=False` и без генерации. Нужна, чтобы менять fusion/порог/буст по замеру,
а не по ощущению.

## Как это работает

```
python -m src.cli rag-eval --golden <файл> --k 5
```

1. модель эмбеддингов прогревается (`_warmup`) - иначе первый вопрос грузит
   sentence-transformers 10-20 с, dense-ветка не успевает в `RAG_TIMEOUT_S`,
   и метрики зависят от порядка вопросов, а не от индекса;
2. L1-кэш очищается перед прогоном;
3. для каждого вопроса выполняется `search()` с профилем/источниками из
   golden-элемента;
4. hits сопоставляются с ожиданиями, считаются метрики, печатается таблица и
   сводка.

## Golden-set

```json
{
  "version": 1,
  "k": 5,
  "items": [
    {
      "query": "вариационное исчисление и методы оптимизации",
      "expect": ["Вариационное исчисление и методы оптимизации"],
      "sources": ["rpd"],
      "profile": "curriculum_design",
      "direction": "09.03.02",
      "year": 2025,
      "note": "title, а не external_id: дисциплина есть в нескольких направлениях"
    }
  ]
}
```

Ключ ожидания - любое из:

| форма | когда использовать |
|---|---|
| `external_id` (`01.03.01:ANN-...pdf`, `competency:пк-2.3`, `skill:python`, hh-id) | документ уникален |
| заголовок (`Теория чисел`) | заголовок уникален, id зависит от направления |
| `source:title` (`rpd:Теория чисел`) | одинаковый заголовок в разных источниках |

Сравнение нормализует регистр, пробелы и `ё/е`. Если ожидание неоднозначно
(много вакансий с одинаковым названием), берите заголовок: иначе набор
наказывает retrieval за то, что тот вернул другой дубль того же документа.

Схема: `python -m src.cli rag-eval --template`. Проверка без поиска:
`--dry-run`. Готовый smoke-набор - `data/reference/rag_golden_smoke.json`
(12 вопросов: РПД, карточки КРМ, вакансии).

## Метрики

- `recall@k` - доля ожидаемых ключей, закрытых в top-k;
- `MRR` - 1/ранг первого релевантного hit (0, если в top-k его нет);
- `nDCG@k` - бинарный gain; каждый ожидаемый ключ учитывается один раз, поэтому
  несколько чанков одного документа не раздувают метрику выше 1.

Вопросы без `expect` в средние не входят (`skipped`).

## Опции

| флаг | смысл |
|---|---|
| `--k` | глубина (по умолчанию 5) |
| `--min-score` | порог уверенности evidence вместо `RAG_MIN_SCORE` |
| `--sweep 0.2,0.3,0.35` | прогнать набор на нескольких порогах и сравнить |
| `--fail-under 0.6` | код возврата 1, если средний recall@k ниже порога (гейт для CI) |
| `--json PATH` | полный отчёт: сводка, по вопросам, top-k, что не найдено |
| `--no-warmup` | не прогревать модель (для отладки деградации) |
| `--template`, `--dry-run` | схема / проверка файла |

## Замер: буст заголовка (2026-11-24)

Индекс: `rpd` 447 док / 2319 чанков, `krm` 644 / 644, `vacancies` 6405 / 12726;
модель `paraphrase-multilingual-MiniLM`, k=5, роль `admin`.

Проблема: dense-ветка ранжирует «похоже по смыслу» и ставит выше документ с
другим названием. Запрос «вариационное исчисление и методы оптимизации»
возвращал «Специальные разделы математики» и «Modern optimization methods»,
а нужная дисциплина не попадала в top-5. Sparse-ветка (FTS) её находила, но RRF
с весами dense 0.6 / sparse 0.4 топила точное совпадение под 50 dense-хитами.

Решение: `apply_title_boost` (`src/rag/retriever.py`) - если заголовок документа
покрывает ≥60% слов запроса (с учётом словоформ по 5-символьному префиксу),
к fused-score добавляется `RAG_TITLE_BOOST * coverage` (по умолчанию 0.35).
`hit_confidence` учитывает `title_score * 0.8`, иначе документ с нужным
названием отсекался бы порогом `RAG_MIN_SCORE` из-за невысокого косинуса.
Выключается `RAG_TITLE_BOOST=0`.

| метрика | без буста | с бустом |
|---|---|---|
| recall@5 | 0.667 | **1.000** |
| MRR | 0.604 | **0.892** |
| nDCG@5 | 0.619 | **0.918** |
| пустых выдач | 0 | 0 |

Оба замера воспроизводимы между прогонами (проверено дважды).

Порог `min_score` на этом наборе не влияет: 0.10-0.35 дают одинаковый recall -
промахи были не из-за отсечения, а из-за ранжирования.

## Что осталось слабым

- Вакансии: длинное описание + короткий запрос - нужный документ бывает ниже
  top-5 (`требования к Data Scientist NLP`). Кандидат на field-boost по
  `key_skills`/заголовку вакансии или на cross-encoder реранк.
- Одинаковые заголовки в разных направлениях: `external_id`-ожидание
  неоднозначно, в golden-set берите заголовок.
- Набор маленький (12 вопросов): метрики чувствительны к составу. Расширять
  до 30-50 вопросов по источникам и держать в `data/reference/`.

## CI-гейт

```bash
python -m src.cli rag-eval --golden data/reference/rag_golden_smoke.json \
    --k 5 --fail-under 0.9 --json reports/rag_eval.json
```

Гейт имеет смысл только на подготовленной БД с построенным индексом
(`rag-index --source all`), поэтому в общий CI его не ставим - запускать
на staging/после реиндексации.
